PLC Agent 完整工程交付流程
===========================

总体链路
--------

用户完整描述需求
  -> Agent 识别工程、代码、设备、网络意图
  -> 补问缺失参数
  -> 创建 devUni 工程
  -> 生成 plc-runtime.json v2
  -> 生成 POU 源码和 devUni 原生工程对象
  -> 校验 ST、任务组态、设备组态和 IO 映射
  -> 把 plc-runtime.json v2 转换为 devUni plc_config.json 和设备配置
  -> matiec 和 ARM GCC 编译
  -> 打包并部署到 PLC
  -> PLC Runtime 加载运行并在线验收


1. 用户给出完整需求
-------------------

例如：

创建一个 SC5100 的 standard ST 工程，工程名 PumpStation，放在 D:\PLC。
主任务周期 20ms，CPU1，优先级1。实现水泵起保停、低液位停机和故障复位。
启动按钮接 %IX0.0，停止按钮接 %IX0.1，接触器接 %QX0.0。
通过 Modbus RTU 控制 1 号变频器，站号1，频率给定寄存器 40001。编译后下发到 PLC。

Agent 先把自然语言整理成内部工程需求：

- 工程信息
- Task 和周期
- POU 与程序实例
- 控制逻辑
- PLC、模块和远程设备
- 网络参数
- IO 映射
- 是否需要编译、部署和启动

地址、寄存器、设备型号或安全行为不明确时，必须向用户澄清，不能自行猜测。


2. Agent 路由任务
----------------

Jev、工作流规则和分类器共同判断请求包含哪些动作，例如：

- devuni_project：创建工程
- st_workspace_delivery：生成或修改 ST 程序
- PLC 组态生成
- 编译与部署

当前工程创建和 ST 交付是两个独立工作流。为了支持“一句话完成整个工程”，后续应增加总工作流：

plc_project_delivery

该工作流依次调度创建工程、生成组态、生成源码、编译和部署，避免不同工作流互相抢占。


3. 创建工程并切换窗口
---------------------

Agent 查询 devUni 候选项并确认：

- 工程类型
- 工程语言
- 设备型号
- 父目录
- 工程名

然后调用 devuni_create_project。

工程创建成功后：

- 新窗口打开新工程。
- 旧窗口继续保留。
- 新窗口创建干净会话。
- 界面只显示一条工程摘要。
- 未完成任务以结构化运行状态保存，不依赖旧聊天历史继续记忆。


4. 生成统一工程模型
-------------------

Agent 在新工程中生成 plc-runtime.json v2，核心结构为：

{
  "schemaVersion": 2,
  "configuration": {},
  "pous": [],
  "devices": [],
  "networks": [],
  "ioMappings": []
}

它是 Agent、IDE 和编译器之间的统一交换格式。

同时生成各个 POU 的 .st 源码。JSON 中只保存 POU 名称、类型和源码路径，POU 正文保存在 .st 文件中。


5. 创建 devUni 原生工程对象
--------------------------

IDE 侧需要提供类似下面的接口：

applyPlcProjectModel(projectRoot, plcRuntimeV2)

该接口根据 v2 创建：

- POU 节点和 .st 文件
- Task
- 程序实例及 Task 绑定
- 设备树
- 网络组态
- IO 映射

用户打开 devUni IDE 后，应看到完整的原生工程树，而不是只有 JSON 和 ST 文件。


6. 校验整个工程
---------------

编译前完成四类检查：

1) ST 语法检查。
2) Task、实例和 POU 引用一致性检查。
3) IO 地址冲突、数据类型和方向检查。
4) 设备型号、网络和协议参数检查。

当前 ST 交付按照以下流水线执行：

validate_st_code
  -> commit_st_delivery
  -> write_file

复杂工程还需要增加多文件工程级事务，保证多个 POU 和组态一起成功或一起失败。


7. 将 plc-runtime.json v2 转换成 devUni 编译输入
------------------------------------------------

这是完整链路中必须存在的格式适配步骤。matiec 和 start.exe 都不能直接读取 plc-runtime.json v2。

plc-runtime.json v2 是面向 Agent、产品和 IDE 的统一工程模型；plc_config.json 是 devUni/PLC Runtime 工具链使用的目标专用中间格式。因此编译前必须执行：

plc-runtime.json v2
  -> devUni 编译适配器
  -> plc_config.json + ST 源文件 + 协议专用设备配置

编译侧实现统一接口，例如：

compilePlcProject({
  projectRoot,
  configPath,
  targetProfile
})

适配器读取 v2 和 .st 文件，按以下规则转换：

- 适配器固定生成 configuration.configuration_name = CONFIG_IEC。
- 顶层 tasks[] -> 每个 Task 生成一个 devUni resources[] 条目。
- task.name/type/priority/cpuCore -> task_name/task_type/priority/cpu_core。
- task.periodMs -> interval，单位从毫秒换算成纳秒。
- instances[].name/pou -> instances[].name/type。
- pous[].source -> 从工程目录读取并复制对应 .st 源文件。
- devices 和 networks -> device_tree 及 EtherCAT、Modbus 等协议专用配置。
- ioMappings 中的本机点位 -> VAR_CONFIG 或 resources[].var_mapped。
- ioMappings 中的远程点位 -> PLC Runtime 的设备驱动通道配置。
- tasks[].deviceId 与 devices[] -> 选择目标设备配置和适配器；当前 devUni 适配固定生成 resource_on = plc。

转换后生成：

- plc_config.json
- POU、GVL、DUT 等 IEC 源文件
- device_tree
- EtherCAT 等协议专用配置文件
- var_mapped
- 目标工具链参数

周期转换规则：

periodMs * 1,000,000 = devUni interval（纳秒）

v2 不保存 Resource 外壳。适配器按 resource_<Task 名> 生成一个 Resource，并把对应 Task 和实例放入其中。

这一步还必须执行目标能力检查。例如目标 profile 不支持 event Task、实例级 retain 或某种网络协议时，应在调用 start.exe 之前明确报错。

传给 start.exe -i 的路径是一次编译的输入工作目录，不是 project/build 输出目录。调用 start.exe 前，适配器需要把目录准备成类似下面的结构：

<compileDir>/
  plc_config.json                 必需；devUni 任务、实例、设备树、数据区和工具链配置
  iec-lib.json                    必需；启用的 IEC/Runtime 库，例如 Native、Motion、Etherlab
  Main.st                         必需；参与编译的 PROGRAM/FUNCTION_BLOCK/FUNCTION 源码
  OtherPou.st                     可选；其他参与编译的 ST 源码
  gloval_var.global.st            可选；轴等设备生成的全局变量，现有插件文件名就是 gloval_var
  slave_config_master_0.json      可选；EtherCAT 等设备或主站的协议专用配置
  hmi_lvgl.json                   可选；工程包含运行时 HMI 时生成
  transLd.txt                     可选；梯形图转换流程使用的中间描述

其中 plc_config.json 至少包含：

- tool_dep_path：matiec、交叉编译器、头文件和库的位置。
- toolchain_gcc：编译器、链接器、CFLAGS、LDFLAGS 和输出扩展名。
- configuration：Resource、Task、实例和 var_mapped。
- device_tree：设备驱动及其协议配置文件引用。
- retain：保持区策略。
- data_area：输入、输出和内存区大小。

当前 devUni 插件只会从工程代码目录复制顶层 .st 文件。若 v2 支持子目录、.gvl 或 .dut，Agent 适配器需要先把它们转换或汇总成 start.exe 能读取的 IEC 源文件，并处理同名文件冲突。

ST 文件是否参与编译，与 PROGRAM 是否绑定 Task 是两件事。当前插件在编译前枚举工程代码目录中的全部顶层 .st 文件，并逐个复制到 .depworkspace。start.exe 再扫描这些 .st，将其中的 PROGRAM、FUNCTION_BLOCK、FUNCTION、TYPE 和全局声明汇总到 generated_plc.st/plc.st。plc_config.json 中的 instances 只决定哪些 PROGRAM 被实例化并由哪个 Task 周期调用；没有直接绑定 Task 的 FUNCTION_BLOCK 和 FUNCTION 仍会作为被调用的类型参与编译。

例如工程代码目录包含：

PLC_PRG.st
FB_Motor.st
ScaleValue.st

调用 start.exe 前，.depworkspace 中也应出现这三个文件。当前检查到的 .depworkspace 只有 PLC_PRG.st，是因为留下该编译快照的示例工程和历史日志都只处理了 PLC_PRG.st。

现有复制逻辑不递归扫描子目录，并且只匹配 .st 后缀。放在子目录中的 ST、独立 .gvl、独立 .dut 不会通过这条路径自动进入编译。这是后续 Agent 编译适配器必须补齐的边界，不能简单复用当前顶层文件枚举。

这里的“工程代码目录第一层”具体指 devUni 工程根目录。插件的组件配置文件位于 <projectRoot>/.devUni，编译时先取得 .devUni，再取它的父目录作为 codeDir，最终枚举的是 <projectRoot>/*.st。例如工程位于 D:\PLC\PumpStation，则当前扫描 D:\PLC\PumpStation\ 直属的 .st 文件，不扫描 D:\PLC\PumpStation\src\ 或其他子目录。

调用示例：

start.exe -i C:\build\run-123\input

start.exe 执行后会在同一个输入目录下创建 project 和 project/build：

<compileDir>/
  plc_config.json
  iec-lib.json
  *.st
  project/
    plc.xml                       从 IEC 源码生成的 PLCopen XML
    build/
      generated_plc.st            汇总后的 POU 和 CONFIGURATION
      plc.st                      加入运行库后的 matiec 完整输入
      POUS.c / POUS.h             matiec 生成的 POU C 代码
      plc_resource_all_in_one.c   Resource 和 Task 调度代码
      plc_task_debugger_data.c    调试变量描述代码
      VARIABLES.csv               变量表
      VARIABLES_DEBUG.csv         在线调试变量表
      Application.so              AArch64 PLC 用户程序动态库
      Application.data            Task、IO、保持区和运行时元数据

compileHash 不属于 start.exe 的必需输入。现有插件在编译完成后生成它，用于判断输入文件是否发生变化和是否需要重新编译。


8. matiec 编译
-------------

适配器执行：

start.exe -i <临时编译目录>

start.exe 汇总生成 plc.st，然后调用：

iec2c.exe plc.st

matiec 输出：

- POUS.c
- Resource 和 Task 对应的 C 文件
- 调试变量描述
- 配置头文件

随后 ARM GCC 把生成的 C 代码编译为 AArch64 的 Application.so。

任务周期、CPU 核、优先级、数据区、IO 驱动和保持区等运行信息被写入 Application.data。


9. 打包和部署
-------------

部署侧建议提供统一接口：

deployPlcApplication({
  device,
  applicationSo,
  applicationData,
  expectedHashes
})

执行顺序：

1) 连接 PLC。
2) 查询当前运行状态。
3) 停止旧应用。
4) 上传 Application.so 和 Application.data。
5) 校验文件哈希。
6) 加载新应用。
7) 启动运行。
8) 读取 Task 状态和诊断。
9) 失败时恢复上一版本。

部署属于高影响操作，Agent 应明确显示目标设备、IP、程序版本和将要执行的动作。


10. PLC Runtime 执行与在线验收
------------------------------

设备端 PLC Runtime：

- 加载 Application.so。
- 读取 Application.data。
- 初始化输入、输出和保持区。
- 按周期、优先级和 CPU 核运行 Task。
- 调用 RESOURCE_*_run__。
- 驱动 EtherCAT、Modbus 和本地 IO。
- 提供变量监控、强制值、诊断和调试接口。

Agent 或 IDE 随后读取 Task 状态、关键变量和设备诊断，确认程序已经加载、Task 正常运行、IO 映射正确。验收失败时停止新应用并执行回滚。
