# Node.js 项目接入 Agent 的通用指南（工具/服务封装）

> 本指南来自一次真实落地：把一个已有的 ST 语言校验器（Langium 语言服务器，可打包为 VSCode 插件）无侵入地接入一个工控 Agent。
> 参考实现就在本仓库，可直接当模板抄：`src/analysis/`（端口层）、`src/app/analyzerHost.ts`（宿主装配）、`scripts/st_analyzer_bridge.cjs`（桥）、`scripts/vendor_st_analyzer.mjs`（vendoring）。

## 1. 适用范围与前置判断

这套模式解决的是同一类问题：

> 我手上有一个已经能跑、但不想改（或改不动）的 Node.js 项目，希望把它的能力暴露给 Agent 或别的程序调用。

先做三条判断，三条都满足就能照抄本指南：

1. 它能产出**可被 Node 直接加载的自包含产物**（单文件 bundle）或**可执行 CLI**；
2. 它是**一次调用一次返回**的模型，不需要长驻会话与长连接；
3. 它**不强依赖调用方的运行时**；如果它依赖 VSCode API，那部分已经被构建时 `external` 掉，或者有官方支持的降级路径。

任何一条不满足，跳到第 6 节选择替代形态（独立服务 / sidecar / 由对方先做 adapter）。

## 2. 总原则：无侵入三要素

**要素一：不改对方源码，只消费它已产出的构建产物。**
对方仓库最多做一件事——在需要更新产物时执行它自己的构建命令。我们不新增、不修改它的任何源文件。

**要素二：新增代码全部落在调用方一侧，且严格分层。**
调用方新增的代码分四层（见第 3 节），平台细节集中在唯一一个宿主装配文件里，核心层不 import 宿主框架（VSCode / Electron / 具体 CLI 框架）。

**要素三：对方产物作为"数据"被复制进调用方的分发单元，运行时零开发机路径。**
用 vendoring 脚本复制 + 记录来源 commit 与 sha256；交付物里 `grep` 不到任何开发机绝对路径。

这三条带来的直接好处：对方可以独立演进（升级只需重跑 vendoring），调用方核心逻辑不动，双方构建/发布解耦。

## 3. 五个交付物（推荐的标准结构）

| 角色 | 职责 | 约束 | 参考实现 |
|---|---|---|---|
| 端口定义 | 输入/输出类型、错误类型、"什么算失败"的唯一判定点 | 纯类型与纯函数，零外部依赖 | `src/analysis/stAnalyzer.ts` |
| 进程执行器端口 | 把"跑子进程"抽象成可替换接口（超时/取消/输出截断/环境白名单） | 上层不认识 `child_process` | `src/analysis/processRunner.ts` |
| 真实实现 | 编码请求 → 调执行器 → 解码响应 | 只依赖执行器接口；路径、运行时、配置全部由构造参数传入 | `src/analysis/spawnStAnalyzer.ts` |
| 降级实现 + 组合器 | 兜底逻辑；主实现不可用时降级并把原因带回结果 | 降级必须可见，绝不假通过 | `src/analysis/fallbackStAnalyzer.ts` |
| 宿主装配 | 产物路径、运行时选择、配置读取、注入内核 | **唯一允许 import 宿主框架的文件** | `src/app/analyzerHost.ts` |

需要强调的两个设计决定：

- **失败语义只有一处**：例如"有 error 级诊断才算失败，warning 只计数"，这个判定必须收在一个函数里（`isStValidationFailure`），不允许在业务代码里重复实现。
- **"实现不可用"与"业务结论是坏的"严格区分**：前者是可降级的 `Unavailable` 错误，后者是正常返回值。把两者混在一起，就会出现"校验器没跑起来 → 报告 0 错误 → 假通过"。

## 4. 统一协议（建议所有工具都按这个来）

### 4.1 调用约定

```
<宿主> --spawn--> 桥脚本
   stdin : 一行 JSON 请求（写完即 close）
   stdout: 仅一行 JSON 响应
   stderr: 全部诊断性输出（日志、警告、堆栈）
   退出码: 0 成功 / 2 环境不可用 / 3 协议或参数错误 / 4 内部异常
```

补充约定：

- **0 表示协议成功，不表示业务结论好**。业务上"发现问题"也是 0，结论放在响应体里。
- 宿主解析 stdout 时取**最后一个以 `{` 开头、以 `}` 结尾的行**。注意：实现只做首尾判断，不做括号平衡校验，所以协议要保证响应体不含裸换行（本例对 message 做了空白折叠来满足这一点）。不要假设 stdout 只有一个换行。
- 响应必须带 `protocolVersion`；宿主必须校验，版本不符按协议错误处理，**不要**当作空结果。

### 4.2 请求/响应参考形状

```jsonc
// 请求
{
  "protocolVersion": 1,
  "workspaceRoot": "F:\\my-workspace",     // 由宿主给出，桥据此构造资源定位
  "targets": [ { "path": "main.st", "text": "..." } ],
  "context": [ { "path": "GVL.st", "text": "..." } ],   // 跨文件语义所需，可为空
  "options": { "maxDiagnostics": 200 }
}

// 响应
{
  "protocolVersion": 1,
  "engine": {
    "id": "st-analyze",
    "bundleMtime": "2026-07-29T11:44:45.000Z",   // 追溯：跑的是哪一版
    "sourceCommit": "bc2112d1"
  },
  "results": [ { "path": "main.st", "diagnostics": [ /* 稳定结构 */ ] } ],
  "contextLoaded": 12,
  "elapsedMs": 214
}
```

### 4.3 结果结构的三条要求

1. **稳定标识优先于文案**：诊断/结果项要有稳定 code（如 `st.type_mismatch`），不要只给人类可读的中文 message；文案会变，code 不会。
2. **保留原文**：把对方原始的 message 与原始 code 一并透传，映射表只做"补充"，不做"替换"。
3. **必须带 engine 字段**：包含实现 id 与可追溯信息（构建产物哈希或 commit、构建时间）。没有它，出问题时无法判断"到底是谁在干活、跑的是哪一版"。

## 5. 桥脚本必备的七个处理

这是最容易漏、也最容易在"开发机能跑、干净机器崩"的部分。逐条对照实现。

**1）噪声隔离——必须在加载对方产物之前完成**

很多库会往 stdout 打警告（例：Chevrotain 解析器的语法歧义提示一次几十行）。如果这些进了 stdout，就会被上层当作响应内容，甚至进模型上下文。

```js
// 必须在 require(目标产物) 之前
const emit = console.log.bind(console);
for (const level of ['log', 'info', 'warn', 'debug']) {
  console[level] = (...args) => process.stderr.write('[' + level + '] ' + args.map(String).join(' ') + '\n');
}
```

**2）零依赖**

桥只允许使用 Node 内置模块。典型坑：目标产物把依赖 bundle 进去了，但**没有导出**某个第三方工具（例：内联了 `vscode-uri` 却没 re-export），而桥所在目录也没有 `node_modules`，于是干净机器上 `require('vscode-uri')` 直接 MODULE_NOT_FOUND。
解决办法是自己写最小实现（本例十来行的 file:// URI 对象），而不是把对方的依赖树复制过来。

**3）环境变量白名单**

只透传运行所需的变量，刻意不继承凭据：

```js
// 与实现保持一致的完整白名单(processRunner.ts 的 ENV_ALLOW_LIST,共 18 项)。
// 若你的目标产物还需要其它变量(例如 locale 相关),在这里显式补充,不要放开全量继承。
const ALLOW = [
  'PATH','Path','PATHEXT',
  'SystemRoot','SYSTEMROOT','windir','WINDIR','COMSPEC',
  'TEMP','TMP','TMPDIR',
  'USERPROFILE','LOCALAPPDATA','APPDATA',
  'NUMBER_OF_PROCESSORS','PROCESSOR_ARCHITECTURE','OS','LANG',
];
function minimalEnv(extra) { /* 只从 process.env 里挑 ALLOW，再合并 extra */ }
```

禁止把 `OPENAI_API_KEY`、`ANTHROPIC_API_KEY`、各种 token 传给被测项目。

**4）显式退出**

如果对方产物在模块顶层启动了监听（例：语言服务器 `startLanguageServer()`、HTTP server、文件 watcher），桥必须主动 `process.exit(code)`，否则进程永远吊住，宿主只能等超时。清理逻辑要放在 `exit` 之前（`finally` 里的代码在 `exit` 之后不会执行）。

**5）超时与取消都杀整棵进程树**

```js
// Windows
spawn('taskkill.exe', ['/pid', String(pid), '/T', '/F'], { windowsHide: true, stdio: 'ignore' });
// POSIX
try { process.kill(-pid, 'SIGKILL'); } catch { child.kill('SIGKILL'); }
```

**6）输出截断与配额**

stdout 上限、stderr 上限（只留前几 KB 进日志）、单次结果条数上限、单文件大小上限、上下文文件数量上限。全部设死，避免一个超大工程把内存和 UI 打爆。

**7）"无法确认"不等于"通过"**

超时、崩溃、协议不符一律归为不可用，交给降级路径处理；**绝不允许**返回看起来像"0 个问题"的空结果。

## 6. 三类目标项目的具体形态

### 6.1 A 类：纯 Node 库 / CLI（已有自包含产物）

- 直接 `require(<产物路径>)`，或 `spawn(<可执行文件>)`。
- 若有 CLI，优先用 CLI（接口更稳定）；桥只做协议转换。
- 若产物是多文件 + 资源文件，**资源文件必须与主产物同目录**（见 6.2 第 3 条）。

### 6.2 B 类：可打包为 VSCode 插件的项目（如 st-analyze）

这类项目通常长这样：TS 源码 + 语言服务器/扩展两个包 + esbuild/webpack 构建 + 一个数据文件（符号表、语法信息）。接入要点：

**1）先确认产物是自包含的。**
检查构建配置里 `external` 只有 `vscode`（甚至没有），运行时 `require` 只涉及 Node 内置模块：

```js
// 快速体检：产物能否在空目录里单独加载
const m = require(path.join(isolatedDir, 'main.cjs'));
console.log(Object.keys(m));
```

**2）插件产物可能在顶层启动 LSP 监听。**
实测：它在模块顶层就 `createConnection(IPCMessageReader(process))` + `startLanguageServer()`。这不妨碍我们 `require` 它并直接调用内部服务，但**必须显式退出**；也正因为这个副作用，**不要**把这类产物直接 `require` 进扩展宿主进程（会抢 stdin、干扰宿主生命周期），要放子进程。

**3）资源文件用 `__dirname` 读取 → 必须与产物同目录。**

```ts
// 目标项目源码里的典型写法（本例三处）
let dirName = __dirname;
let data = readJsonFile(`${dirName}\\data.json`);
```

所以 vendor 目录必须是**平铺的三个文件**：`main.cjs` + `data.json` + `bridge.cjs`。不能挪目录、不能改名、不能"内联成一个文件"。

**4）优先用内部服务接口，而不是走 LSP 协议。**
如果产物导出了服务集合（本例 `const { shared, st } = require('./main.cjs')`），直接调内部入口，比实现 LSP 客户端简单得多，也少一整层协议：

```js
const { shared, st } = require('./main.cjs');
const doc = shared.workspace.LangiumDocumentFactory.fromString(text, uri);
shared.workspace.LangiumDocuments.addDocument(doc);
await shared.workspace.DocumentBuilder.build([doc], { validation: false });
const diagnostics = await st.validation.DocumentValidator.validateDocument(doc);
```

只有当对方**没有**导出可用服务、只暴露 LSP 时，才退回"宿主实现 LSP 客户端 + didOpen/等 publishDiagnostics"（复杂度高一档）。

**5）工作区感知型分析器必须喂上下文。**
本例校验器是工作区感知的：孤立片段会大量误报 `Could not resolve reference`。所以协议里带 `context` 字段，由调用方读工作区相关文件后一起提交。**不要**指望"只校验一段文本"能给出准确结论。

**6）Windows-only 的硬编码要提前识别。**
本例源码三处 `${__dirname}\\data.json` 用了反斜杠，Linux/macOS 上读不到资源文件。若只面向 Windows（本例如此）可接受并写进文档；若要跨平台，需要对方修——这属于"必须改对方源码"的少数情况，要提前确认。

**7）宿主侧的运行时选择。**
扩展宿主里 `process.execPath` 通常指向 `Code.exe`（Electron），不是 node。做法：给这个候选始终带 `ELECTRON_RUN_AS_NODE=1`（真正的 node.exe 会忽略它），并给出候选链与可配置覆盖：

```
配置的 nodePath → 环境变量 → PATH 里的 node → 扩展宿主自带运行时(加 ELECTRON_RUN_AS_NODE=1)
```

多个候选按顺序试，第一个跑通的即采用；全部失败才降级。

### 6.3 C 类：需要长驻会话 / 高频调用

冷启动成本实测（本例，注意口径）：桥自报的 `elapsedMs` 约 **200ms/次**（加载约 60ms + 首次执行约 150ms）；按含 Node 进程启动的墙钟算是 **约 340 到 385ms/次**，比桥内部口径高约 1.7 倍——对外承诺耗时请用墙钟口径。同进程连续复用实测约 **2ms/次**（同一进程内连跑 5 次共 10ms），但本项目**尚未实现常驻形态**，这个数字只代表"进程内重复调用"的理论下限，不代表已有能力。因此：

- 低频（每次用户提问一两次）：一次性子进程，简单可靠；
- 高频或交互式：常驻进程 + 请求队列（内部索引是共享可变状态，**必须串行**）+ 空闲超时退出 + 崩溃自动重启；
- 跨语言/跨机器：包一层 HTTP 或 stdio 服务，端口定义不变，只换实现。

## 7. 宿主侧接线清单

接入方需要新增/修改的地方，按"改动最小化"列出来（本例的实际改动量）：

| 位置 | 改动 | 规模 |
|---|---|---|
| 端口/执行器/实现/降级/上下文收集 | 新增 6 个文件（src/analysis，对应第 3 节前四个角色 + 工作区上下文收集） | 约 500 行，纯 Node，可单测 |
| 宿主装配 | 新增 1 个文件：产物路径 + 运行时候选 + 读配置 + 产实例 | 约 110 行，唯一 import 宿主框架 |
| 工具实现 | 把原工具的执行体换成调用端口（参数语义保持向后兼容） | 约 60 行 |
| 配置声明 | 新增 8 个配置项 + 2 个 npm script | 约 60 行声明 |
| 持久化结构 | 增加一个纯数据字段：把设置随运行记录持久化，重试/续跑用同一套配置 | 约 20 行 |
| 运行协调器 | 注入工厂，在展开运行配置的两处补两行 | 约 10 行 |
| 宿主入口 | 装配工厂并注入协调器；发消息时写入设置 | 约 5 行 |
| vendoring | 新增 1 个脚本 + gitignore 忽略产物 | 约 100 行 |

两个关键约束：

- **持久化里存纯数据，不存实例**。函数与实例不能序列化；重试/续跑时由工厂按持久化设置重新构造实例。
- **字段命名避免与内核已有字段冲突**。本例一开始把持久化字段命名为 `stAnalyzer`，与内核的实例字段同名，展开时类型冲突；改名为 `stAnalyzerSettings` 后解开。这个坑值得提醒。

## 8. 降级矩阵（必须显式设计，不能靠意外）

| 触发 | 行为 | 结果标记 |
|---|---|---|
| 功能开关关闭 | 用兜底实现 | `engine.id=fallback` + 原因 `disabled` |
| 产物缺失 / 入口找不到 | 用兜底实现 | 原因 `bridge_missing` |
| 加载失败 / 缺资源文件 / 退出码 2 | 用兜底实现 + stderr 摘要进日志 | 原因 `unavailable` |
| 超时 | **按失败处理，不降级为通过** | 原因 `timeout`，`ok=false` |
| 无 JSON / 版本不符 | 用兜底实现 | 原因 `protocol_error` |
| 用户取消 | 杀进程树；以异常向上传播，由运行层判定为 cancelled | 无本层标记（运行层状态，桥和端口层都不产生这个值） |
| 单目标超限（大小/数量） | 跳过并提示 | 独立告警码 |

原则三条：降级必须可见；"无法确认"不等于"通过"；兜底链末端始终有一个不依赖外部依赖的实现（本例就是原来那套简易校验），保证离线可用。

## 9. 安全与配额

- **路径边界**：所有文件读取走调用方已有的工作区边界校验（禁止 `../` 与区外绝对路径）。
- **读取配额**：只读需要的扩展名；上下文文件数量上限、单文件大小上限、遍历时跳过 `node_modules/.git/dist` 等。
- **进程能力**：`shell: false` 且参数以数组传递（杜绝命令注入）；工作目录固定；环境变量白名单。
- **输出限额**：桥侧截断 + 调用方兜底截断，双层保险。
- **审批分级**：只读能力免审批、风险级别最低；写文件/执行命令/设备写入必须走审批与副作用账本。不要把只读分析和有副作用的操作放在同一层级。
- **凭据隔离**：绝不把 API Key 传给工具进程。

## 10. 可观测性

工具回执里必须让人（和模型）一眼看出"这次是谁在干活、干了多久、是不是降级了"：

```jsonc
{
  "engine": "st-analyze",
  "errorCount": 2,
  "warningCount": 1,
  "elapsedMs": 272,
  "analyzer": { "detail": "bundle=2026-07-29T11:44:45.000Z commit=bc2112d1" },
  "context": { "files": 12, "truncated": false }
}
```

再配三条通道：

- **审计事件**：工具请求/完成带 engine、耗时、结果计数、降级原因；
- **输出面板**：桥的 stderr（截断后）只进日志通道，绝不进模型上下文；
- **持久化摘要**：运行记录里只存摘要（引擎、错误数、前几条 code），不存全量结果，避免存储膨胀。

## 11. 可验证性：怎么证明"真解耦"

四条证据，缺一不可（本例全部通过）：

1. **依赖方向检查**：核心层目录里 `grep` 不到宿主框架的 import（本例：`runtime/analysis/tools/protocol/policy/workspace` 里没有 `vscode`）。
2. **单测不启动宿主**：注入假执行器，覆盖加载失败、超时、噪声、坏 JSON、协议版本不符、候选链回退、取消传播、降级可见。
3. **脱离宿主可独立运行**：提供一个纯 Node 的 CLI 入口，用同一套端口实现跑通——这是"能搬到 CLI/边缘服务"的实证，不是口号。（本例已落地：`scripts/st_analyzer_cli.mjs`，它本身就是一个最小宿主范例；前置 `npm run test:generate` 生成端口层产物、`npm run vendor:st-analyzer` 准备被校验产物。）
4. **换实现零改内核**（范围要说清：只对"同一端口的实现替换"成立；**首次接入一个新工具必然要动内核侧**，见第 7 节）：把子进程实现换成常驻/远程实现时，内核与运行协调器一行不改。

推荐的测试矩阵（本例的 `scripts/st_analyzer_test.mjs` 就是按这个写的）：

| 用例 | 断言要点 |
|---|---|
| 稳定码映射 | 各模式的 message → 期望 code；有原始 code 时优先用原始值；未命中落到 `other` |
| 严重度语义 | error 才算失败；warning/info 只计数；未知严重度按 error（保守） |
| 响应解析 | 合法响应、坏 JSON、空输出、版本不符、severity 数字映射 |
| 假执行器：失败分支 | 退出码 2/3/其他、超时、执行器抛异常 → 对应错误码 |
| 候选链 | 第一个候选失败、第二个成功；全部失败 → 抛最后一个原因 |
| 取消传播 | 已取消时原始异常向上抛，不被包装成"可降级" |
| 降级可见 | 主实现不可用 → 兜底结果 + `fallbackReason` 正确 |
| 真实进程 | 噪声 stdout 取最后一行 JSON；超时能杀掉进程 |
| 真实端到端（产物存在才跑） | 正确输入 0 错误、构造错误能报出稳定 code、跨文件上下文生效 |
| 持久化守卫 | 合法设置能存取；非法设置被拒且不影响旧记录读取 |

## 12. 常见坑清单（都是实测踩过的）

1. **不要用文件时间戳判断产物新旧**。本例先用 mtime 判断"产物落后于源码"，误报了；hash 比对证明两版字节完全一致。用 sha256 + git commit。
2. **资源文件必须与主产物同目录**（`__dirname` 读取），不要做目录整理。
3. **孤立片段校验会误报**。工作区感知型分析器必须支持喂上下文。
4. **stdout 会被对方库污染**。必须在加载前劫持 console，并且用"取最后一个 JSON 行"容错。
5. **不要假设能复用对方的 node_modules**。桥可能不在对方项目目录内，解析不到依赖；保持零依赖。
6. **产物可能在顶层有副作用**（启动监听），必须显式退出，且不要放进宿主进程。
7. **持久化字段命名要和内核字段区分**，否则展开配置时类型冲突。
8. **降级路径必须能被测试断言**，否则"没跑起来"会被误当成"没问题"。
9. **能力边界要写进工具说明**。本例校验器有三个盲区（内置 FB 参数类型、用户自定义 FB 参数类型、残缺语句），所以描述里明确"不要当成可上机运行的证明"，避免模型过度宣称。
10. **vendoring 脚本里也不要写死开发机路径**，只用参数/环境变量，保证交付物里 `grep` 不到。
11. **BOM 会导致静默漏报**（实测发现）：Windows 工具链生成的文本文件常带 UTF-8 BOM，本例的校验器遇到 BOM 开头的输入会返回"0 诊断"而不是报错——这是最危险的一类失败。宿主在把文本交给桥之前必须剥掉 BOM（CLI 实现里就是这么做的）。

## 13. vendoring：产物怎么进交付物

核心要求：**交付物里不出现任何开发机路径**，且能追溯"这份产物从哪来"。

```
vendor/<tool-name>/
├─ bridge.cjs       ← 我们写的桥（入库，属于我们的代码）
├─ main.cjs         ← 对方构建产物（不入库，由脚本复制）
├─ data.json        ← 对方运行所需资源（必须与 main.cjs 同目录，不入库）
└─ vendor.json      ← 来源 commit、构建时间、各文件 sha256（入库）
```

vendoring 脚本必须遵守：

1. **不写死默认路径**，只认参数或环境变量（本例 `ST_ANALYZER_SRC`）。这样交付物里 `grep` 不到开发机目录名。
2. **复制后记录 sha256 与 git commit**；本次与上次相同时打印 `unchanged`，避免制造无意义差异。
3. **产物目录加入 .gitignore**（与 `dist/` 同样的习惯），但 `vendor.json` 与桥脚本要入库。
4. **打包钩子**：把 vendoring 挂到发布前的钩子（本例 `vscode:prepublish` → `compile` + `vendor:st-analyzer`），保证打出来的包一定带产物。
5. **缺失时优雅降级**：没设置环境变量且 vendor 目录已有产物 → 复用；两者都没有 → 明确报错（不要产出半成品包）。

三种交付形态的选择：

| 形态 | 适用 | 代价 |
|---|---|---|
| 产物随宿主打包（本例） | 宿主与工具一起交付、离线可用 | 宿主体积 +1MB 量级；升级需重新打包 |
| 发布为 npm 包 | 多个宿主共用同一工具 | 需要对方提供 headless 入口；宿主侧要处理依赖 |
| 独立服务（HTTP/stdio） | 高频、跨语言、跨机器 | 需要部署与运维；冷启动摊销后性能更好 |

> 我有一个已存在的 Node.js / 可打包为 VSCode 插件的项目，路径：`<填路径>`。
> 它已经能构建出可用产物（`<填产物路径，例如 src/xxx/out/main.cjs>`），运行时需要的资源文件是 `<填，例如 out/data.json>`。
>
> 请把它的能力封装成一个能被其他程序调用的工具。**硬性要求：**
>
> 1. 不要修改它的任何源码，也不要改它的构建流程；最多在需要更新产物时执行它自己的构建命令。
> 2. 新增一个桥脚本，契约是：stdin 一行 JSON 进、stdout **仅**一行 JSON 出，其他所有输出（日志、警告、堆栈）一律走 stderr；退出码 `0` 成功 / `2` 环境不可用 / `3` 协议或参数错误 / `4` 内部异常；响应必须带 `protocolVersion` 和 `engine`（含实现 id、产物哈希或 git commit）。
> 3. 桥在加载目标产物**之前**必须把 `console.log/info/warn/debug` 重定向到 stderr；如果目标产物顶层启动了什么监听，桥要显式 `process.exit`，且清理逻辑放在 exit 之前。
> 4. 桥只使用 Node 内置模块，**不新增任何运行时依赖**；只透传必要的环境变量白名单，绝不继承任何密钥类变量。
> 5. 调用方按端口模式实现，分五件：端口定义（输入输出类型 + 唯一的失败判定）、进程执行器端口（可注入，方便单测）、真实实现（只依赖执行器）、降级实现 + 组合器、宿主装配（产物路径/运行时选择/配置读取，且是唯一允许 import 宿主框架的文件）。
> 6. 目标产物与它的资源文件必须复制到同一目录（对方可能用 `__dirname` 读取资源），不要分开放、不要改名。
> 7. 运行时可执行文件要有候选链（配置指定 → 环境变量 → PATH 里的 node → 宿主自带运行时，后者带 `ELECTRON_RUN_AS_NODE=1`），按顺序试，全部失败才降级。
> 8. 超时与用户取消都要杀掉整棵进程树（Windows 用 `taskkill /T /F`）；超时按失败处理，**绝不允许**返回"看起来没问题"的空结果。
> 9. 如果对方是分析类/编译类工具且是工作区感知的，协议要能一次提交多个文件（目标 + 上下文），否则会有大量假阳性。
> 10. 给我一个 vendoring 脚本：把产物与资源复制到 vendor 目录，记录来源 commit 与各文件 sha256，不写死开发机路径；同时给出交付物里 `grep` 不到任何开发机绝对路径的确认。
> 11. 证明解耦：核心层不 import 宿主框架；单测注入假执行器覆盖"不可用/超时/噪声/坏 JSON/版本不符/取消/降级可见"；再给一个纯 Node 的 CLI 入口，能脱离宿主直接跑通。
> 12. 工具返回里必须包含：实现 id、耗时、结果计数、是否降级及原因；能力边界要写进工具说明（哪些情况它检不出来）。

## 15. 最小公约（三条，建议全组统一）

1. **协议统一**：一行 JSON 进、一行 JSON 出；退出码四值语义；必须带 `protocolVersion` 与 `engine`。
2. **结构统一**：端口 + 执行器 + 实现 + 降级 + 宿主装配，五件套；名字可以不同，分层必须一致。
3. **回执统一**：工具返回里必须有实现标识、耗时、失败原因、以及"是否降级"这一项，让模型和审计都能看懂这次是谁在干活。

按这三条做，**同一端口的实现替换**（子进程 → 常驻 → 远程）不需要改内核与运行层。但必须诚实：**首次接入一个新工具时，内核侧必然有改动**——工具注册、配置槽位、协调器注入、持久化字段，本例正是如此（见第 7 节的清单）。统一协议与统一分层买到的是：从第二个工具起，接入成本收敛到"端口 + 工具"两层，并且所有工具的回执、降级、观测口径一致。
