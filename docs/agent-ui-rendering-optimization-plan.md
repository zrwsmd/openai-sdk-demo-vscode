# Agent UI 渲染优化计划

本文记录聊天回复区域的渲染优化方向。目标是让输出既更丝滑，也更易读：不要把 Markdown 原文粗糙
显示给用户，而是把表格、代码块、列表、标题、inline code 等结构渲染成清晰的 UI。

## 当前问题

当前 `media/main.js` 的 `renderRich()` 只做了很少的处理：

- 每次渲染都会 `bubble.textContent = ''`，清空并重建整个回复 bubble。
- 只识别三反引号代码块。
- 普通文本只按段落和简单列表排版。
- Markdown 表格不会变成真正的表格，只会原样显示成 `| 文件 | 依赖 | 被依赖 |`。
- `**重点**`、inline code、标题层级等结构没有完整渲染。
- `scrollBottom()` 直接设置 `messagesEl.scrollTop = messagesEl.scrollHeight`，多个事件都会调用。

这些问题会造成两类体验下降：

- 回复越长，流式更新越容易卡，因为每个 `text.delta` 都可能触发整块 DOM 重建。
- 表格、依赖关系、分析结论等内容缺少结构层次，看起来像一大块文本。

## 优化原则

- 不显示 Markdown 标记本身，而是把 Markdown 结构渲染成 UI。
- 不引入大型前端框架；优先用原生 DOM 和少量解析逻辑。
- 流式文本是只增不减的，优先做追加式渲染，避免每次从头重建。
- 滚动按帧节流，一帧最多执行一次 scroll-to-bottom。
- 代码块、表格、标题、inline code 要有清晰视觉层级，但不要做花哨装饰。

## 阶段顺序

### 1. `scrollBottom()` 按帧节流

问题：

当前滚动函数是直接同步执行：

```js
messagesEl.scrollTop = messagesEl.scrollHeight;
```

多个事件都会调用它，流式输出、工具回执、thinking、诊断卡片都可能触发滚动。

建议：

- 增加一个 `scrollFramePending` 标记。
- `scrollBottom()` 内只安排一次 `requestAnimationFrame`。
- 一帧内多次调用合并成一次。

收益：

- 风险低，不碰 agent 状态机。
- 可以减少流式输出时的布局抖动和重复滚动计算。

验证：

- `node --check media/main.js`
- 手动验证长回复、工具调用后回复、thinking 展开折叠。

### 2. `renderRich()` 从清空重建改为追加式渲染

问题：

当前每次渲染都会：

```js
bubble.textContent = '';
```

然后把已有文本重新拆段、重建 DOM。流式文本越长，重建成本越高。

建议：

- 为每个 agent bubble 保存已渲染文本长度和尾部解析状态。
- 流式增量只追加新增部分。
- 对 final/replay/history 这类非流式场景，可以继续一次性完整渲染。
- 遇到需要重排的复杂结构，例如未闭合代码块或表格行跨 chunk，可以允许局部重渲染当前块，而不是整块 bubble。

注意：

- 追加式渲染要保留工具调用后“最终答案移动到工具回执下面”的现有顺序逻辑。
- 不能改坏之前修过的 Thinking 顺序问题。

验证：

- 长文本流式输出不明显卡顿。
- 工具调用后最终总结仍显示在工具回执后面。
- 停止、继续、重试后 UI 顺序不乱。

### 3. Markdown 表格渲染为真正的 table

问题：

类似下面的 Markdown 表格当前会原样显示：

```text
| 文件 | 依赖 | 被依赖 |
|---|---|---|
| st-refs/PumpControl.st | MotorControl | — |
```

这会让用户看到一堆竖线和横线，而不是表格。

建议：

- 识别连续的 Markdown table block。
- 渲染成 `<table>`、`<thead>`、`<tbody>`。
- 单元格内继续支持 inline code。
- 表格容器横向可滚动，避免窄侧边栏挤爆布局。

样式目标：

- 标题行加粗。
- 行分隔清楚。
- 文件名/符号可用链接色或强调色。
- 表格不要套进额外大卡片，保持和正文自然衔接。

验证：

- 依赖分析表格可读。
- 长文件名不撑破容器。
- 移动/窄宽度下可横向滚动。

### 4. 优化代码块和 ASCII 依赖图

问题：

依赖关系图、ASCII 树、ST 代码片段需要像图块一样展示，有内边距、暗色背景、等宽字体和清晰边界。

建议：

- 保留三反引号代码块解析。
- 对疑似 ASCII 图或依赖图的代码块使用统一 `pre` 样式。
- 增加代码块内边距、圆角、轻边框、横向滚动。
- 语言标签可以隐藏或简化显示，不要占太多空间。

样式目标：

- 类似“依赖图被独立成块展示”，一眼能扫出结构。
- 不要把代码块做得像复杂卡片；它只是内容块。

验证：

- ST 代码块可读。
- 依赖树和箭头关系不换行错位。

### 5. 渲染标题、重点和 inline code

问题：

当前 `**重点**`、`inline code`、章节标题没有完整结构化渲染。

建议：

- 支持 `**bold**` 转成 `<strong>`。
- 支持 `` `inline code` `` 转成 `<code>`。
- 识别 Markdown 标题 `#` / `##` / `###`，转换成紧凑标题样式。
- 保留当前“短行像标题”的启发式，但避免误把普通短句都放大。

样式目标：

- “详细分析”“几个需要关注的点”看起来像标题。
- `FB_RateLimiter`、`VAR ... END_VAR` 这类内容显示成小代码胶囊。
- 不再把 `**`、反引号等 Markdown 标记直接暴露给用户。

验证：

- Markdown 标记不裸露。
- 中文正文行距舒服。
- inline code 不撑高行距太多。

### 6. 段落、列表和编号优化

建议：

- 支持 `- item`、`* item`、`• item`、`1. item`、`1、item`。
- 列表间距比普通段落更紧凑。
- 嵌套列表暂时可以不做，避免解析复杂度上升。
- 中文编号和英文编号都要显示自然。

验证：

- 模型输出的常见列表不会变成普通段落。
- 列表不会和前后正文粘在一起。

## 与模型提示词的关系

UI 渲染优化优先于强行要求模型“不输出 Markdown”。后续可以提示模型“可以使用表格、代码块和列表”，
但 UI 必须负责把这些结构显示好。

核心目标是：

- 模型可以输出结构化 Markdown。
- 用户看到的是漂亮表格、代码块、标题和 inline code。
- 不再要求模型为了 UI 缺陷牺牲表达能力。

## 完成标准

- 长回复流式输出更顺，不因全文 DOM 重建明显卡顿。
- Markdown 表格被渲染成真正表格。
- 代码块/依赖图成为独立可读内容块。
- 标题、重点、inline code 有明确层次。
- 不再裸露常见 Markdown 标记。
- 不破坏工具卡片、Thinking 顺序、暂停/继续/重试、历史回放。
